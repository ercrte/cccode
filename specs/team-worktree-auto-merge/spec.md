# JulyCode 多 Agent Worktree 自动合并 Spec

## 背景

JulyCode 已支持长期团队、带依赖的共享任务、成员持久会话和独立 Git Worktree。代码任务只有在成员 Worktree 无未提交或未跟踪修改、并产生可验证的新提交后才能完成。当前团队全部任务完成后，Lead 只汇总成员分支，用户仍需手工判断合并顺序、处理依赖并执行 Git 合并。

本阶段为长期团队补充自动合并闭环：代码任务完成时先串行进入团队内部集成基线，使后续依赖任务能够看到上游代码；全部任务完成后，再把完整成果一次性发布到 Lead 的目标分支。任何冲突或状态不安全都不得污染 Lead 工作目录或产生部分发布。

本文中的“集成轮次”是指：从上一轮成功发布或确认无需发布之后，团队首次新增或重新打开任务开始，到这批任务全部成功完成并发布或确认无需发布为止。发布前继续新增或重新打开的任务归入当前轮次；发布后新增或重新打开的任务进入下一轮。历史轮次已经发布的提交不重复集成。

调研依据：

- [Git merge 官方文档](https://git-scm.com/docs/git-merge)指出，在带未提交修改的工作区执行合并可能难以完整中止和恢复，因此发布前必须保护 Lead 工作目录。
- [Git merge-tree 官方文档](https://git-scm.com/docs/git-merge-tree.html)说明合并可以在不触碰当前索引和工作目录的情况下预演或构造结果，为隔离集成提供了安全基础。
- [Claude Code Worktree 文档](https://code.claude.com/docs/en/worktrees)与[Codex 多 Agent Worktree 介绍](https://openai.com/index/introducing-the-codex-app/)均将 Worktree 用作并行 Agent 的文件隔离边界，并强调保留、检查和安全应用成果。

## 目标

- 让长期团队的已完成代码成果无需人工逐分支合并即可形成一个完整结果。
- 让有依赖关系的代码任务在开始执行前看到已集成的上游成果。
- 保证成员并发完成时按串行、一致且可恢复的方式集成。
- 保证最终发布要么完整成功，要么不改变 Lead 分支和工作目录。
- 为成功、冲突、拒绝发布和恢复过程提供清晰、可追溯的中文状态。

## 功能需求

- F1: 自动合并只适用于长期团队中的代码任务。研究任务、普通主 Agent、一次性子 Agent 以及未使用团队的工作流必须保持现有行为。
- F2: 每轮团队代码集成开始时，系统必须记录 Lead 当前检出的命名分支和提交作为本轮目标与发布基线。若 Lead 处于游离提交状态、仓库正在执行其他 Git 集成操作，或无法唯一确认目标分支，则本轮代码任务不得开始集成。
- F3: 成员领取代码任务前，系统必须先确认其 Worktree 无未提交、未跟踪或未纳入团队集成的额外提交，并使其工作分支前进到最新团队集成基线。同步失败时不得开始任务，且必须说明阻塞原因。研究任务不执行此同步。
- F4: 成员申请完成代码任务时，系统必须继续校验任务提交来自该成员、位于任务起点之后、是成员分支当前结果，并且成员 Worktree 干净。校验失败的任务不得进入团队集成。
- F5: 通过校验的代码任务必须先串行合入团队内部集成基线，再被视为成功完成。只有内部集成成功后，依赖该任务的后续任务才可解除阻塞；后续代码任务必须从包含该成果的最新基线开始。
- F6: 多个独立成员并发完成代码任务时，系统必须逐个集成并持久记录已接受顺序。每个任务只能被接受一次；重复请求、事件重放或重启恢复不得生成重复提交或重复合并结果。
- F7: 内部集成发生内容冲突、提交缺失、提交归属不匹配或 Git 状态无法确认时，系统不得自动选择任一方内容，不得改写成员提交，也不得把该任务标记为成功完成。冲突必须与其他已接受成果隔离，并报告任务、成员、提交、冲突路径和可执行的修复提示。
- F8: 内部集成失败不得改动 Lead 分支、Lead 索引或 Lead 工作目录；成员 Worktree、成员分支、任务提交和此前已接受的团队成果必须保留，以便成员修复后重试。
- F9: 当且仅当本轮所有任务均成功完成、所有代码任务均已进入内部集成基线时，系统才可尝试最终发布。若本轮没有代码任务，则必须明确报告“无需发布”，且不创建空合并结果。
- F10: 最终发布前，系统必须确认 Lead 仍位于本轮记录的目标分支、目标分支仍指向记录的发布基线、Lead 工作目录和索引均干净、没有未跟踪文件，也没有正在进行的合并、变基、挑拣或回滚操作。任一条件不满足时必须拒绝发布并保留完整内部成果。
- F11: 最终发布必须一次性把内部集成的完整结果应用到 Lead 目标分支，并同步更新 Lead 工作目录。发布结果必须保留每个成员任务提交的可追溯性。不得出现只发布部分任务成果后再报告整体失败的状态。
- F12: 最终发布期间若目标分支被其他进程推进、Git 操作失败或状态变得不安全，系统必须停止发布；若发布尚未完成，Lead 分支和工作目录必须保持发布前状态，内部成果继续保留并允许幂等重试。
- F13: 发布成功后，系统必须尝试让所有空闲且干净的成员 Worktree 前进到已发布基线，使下一轮代码任务从一致版本开始。不能安全前进的成员必须保留现场并标记为待同步；该成员在问题解决前不得领取新的代码任务，但不得回滚已经成功发布的 Lead 分支。
- F14: 团队必须持久记录本轮目标分支、发布基线、已接受代码任务、对应成员与提交、集成顺序、发布状态和最近失败原因。JulyCode 重启或重新打开团队时必须从 Git 事实与持久状态恢复，不得丢失已接受成果或把未完成发布误报为成功。
- F15: 团队状态、等待事件和最终回复必须展示可观察的集成摘要。成功时至少包含目标分支、发布结果和已集成代码任务；失败或拒绝时至少包含所处阶段、未发布原因、受影响任务或成员以及成果保留位置。
- F16: 在最终发布成功前，Lead 不得向用户宣称团队代码目标已经完成；应明确区分“任务已完成但待发布”“内部集成失败”“发布被安全检查拒绝”和“已成功发布”。
- F17: 所有用于集成的仓库、路径、分支和提交都必须来自已校验的团队、花名册、任务和 Git 状态，不能由模型通过自由文本指定任意目标。自动合并不得推送远端、强制更新分支、自动变基、自动解决冲突或删除团队数据、成员 Worktree 及成员分支。
- F18: 已完成任务被显式重新打开时，系统必须把它作为当前或下一集成轮次中的新任务尝试处理。先前已发布记录继续保留，新尝试必须产生并集成新的有效提交，不能覆盖历史记录或因为复用任务标识而被误判为重复请求。

## 非功能需求

- N1: 安全优先。任何无法确认的 Git 状态都必须按失败处理，不能以“可能成功”推进任务或发布。
- N2: 同一团队的集成和发布必须串行；多个团队或进程同时操作时不能交错破坏分支、任务状态或持久记录。
- N3: 内部集成和最终发布必须可中断、可恢复、可幂等重试；进程崩溃不能留下被误判为成功的半完成状态。
- N4: 自动合并不得依赖模型判断 Git 命令是否成功；状态必须通过可验证的 Git 事实和持久记录确定。
- N5: 错误信息必须使用中文、包含可操作上下文并对敏感内容脱敏；单个团队的集成失败不得中断 JulyCode 主会话或其他团队数据。
- N6: 既有权限、Hook、任务审批、上下文隔离、Worktree 清理保护和团队恢复语义必须继续生效。
- N7: 功能必须通过临时真实 Git 仓库中的单元与集成测试，以及 tmux 中至少一个真实多成员对话场景验收。

## 不做的事

- 不为一次性 `isolation: worktree` 子 Agent 自动提交或自动合并成果。
- 不自动推送远端、创建 Pull Request 或操作远程托管平台。
- 不使用模型或启发式规则自动解决内容冲突。
- 不在 Lead 工作目录 dirty、目标分支变化或 Git 操作未完成时自动 stash、reset、clean 或强制发布。
- 不自动修改、压缩、重排或丢弃成员已有提交。
- 不自动删除长期团队、任务历史、邮箱、成员会话、成员 Worktree 或成员分支。
- 不实现跨仓库、跨机器或跨用户的分布式合并。

## 验收标准

- AC1: 普通聊天、一次性子 Agent、研究任务和非团队流程的 Git 行为保持不变；只有长期团队代码任务进入自动集成。（覆盖 F1）
- AC2: 第一项代码任务开始时能够记录 Lead 命名目标分支与发布基线；游离提交或已有 Git 集成操作会在成员写代码前明确失败。（覆盖 F2）
- AC3: 上游代码任务内部集成成功后，不同成员领取其依赖任务时能直接读取上游成果；成员 Worktree dirty、含未跟踪文件或含额外提交时领取被拒绝且现场不变。（覆盖 F3、F5）
- AC4: 非当前成员提交、任务起点之前的提交、非当前分支结果或 dirty Worktree 均不能完成代码任务，也不会改变内部集成状态。（覆盖 F4）
- AC5: 两个成员并发完成独立代码任务时，两项成果均被串行接受、顺序被记录、依赖正确解锁；重复完成请求和事件重放不会产生重复结果。（覆盖 F5、F6）
- AC6: 两个成员修改同一内容并产生冲突时，后一个任务不会被标记完成；Lead 分支和工作目录不变，成员分支及此前成果仍存在，错误列出冲突路径和修复方向。（覆盖 F7、F8）
- AC7: 团队包含失败、取消、未集成或仍在运行的任务时不会尝试最终发布；只有研究任务的团队报告无需发布且不产生空提交。（覆盖 F9、F16）
- AC8: Lead 工作目录 dirty、存在未跟踪文件、目标分支变化、目标提交变化或存在其他 Git 集成操作时，最终发布被拒绝，完整内部成果可在条件恢复后重试。（覆盖 F10、F12）
- AC9: 多个代码任务全部成功后，Lead 目标分支和工作目录一次性出现全部成果，每个任务提交均可追溯，不存在部分发布状态。（覆盖 F11）
- AC10: 最终发布与外部目标分支更新发生竞争时至多一方成功；失败方不覆盖新提交、不强制更新目标，重试不会重复集成已有成果。（覆盖 F6、F12）
- AC11: 发布成功后，空闲且干净的成员都从已发布基线继续；无法安全同步的成员被标记并阻止领取新代码任务，但 Lead 已发布结果保持不变。（覆盖 F13）
- AC12: 在内部集成前、集成后持久化前、最终发布前和发布后记录前分别模拟进程中断，重启后均能根据 Git 事实恢复为正确状态，不丢成果、不重复合并、不误报成功。（覆盖 F14、N3）
- AC13: 团队状态、等待结果和最终回复能区分待发布、内部冲突、安全拒绝和发布成功，并展示目标分支、任务、成员、提交或保留位置等对应信息。（覆盖 F15、F16）
- AC14: 自由文本中的伪造路径、分支或提交不能改变集成目标；自动流程不执行 push、force、stash、reset、clean、rebase、自动冲突解决或团队数据删除。（覆盖 F17）
- AC15: 已发布代码任务重置为待处理并再次完成时，新提交只在新轮次集成一次；旧提交仍可追溯，重复请求仍保持幂等。（覆盖 F6、F14、F18）
- AC16: 既有团队、Worktree、权限、Hook、任务审批、会话恢复、一次性子 Agent 和全项目测试无回归。（覆盖 N5、N6）
- AC17: 在 tmux 中启动 JulyCode，通过真实对话创建至少两个 Worktree 成员及含依赖的代码任务；上游成果自动进入下游成员基线，全部完成后 Lead 分支一次性获得完整代码并明确回复已发布。另一个冲突对话中，Lead 分支保持原样且回复包含冲突路径和保留成果。（覆盖 F1-F18、N7）
