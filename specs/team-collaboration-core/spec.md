# MewCode 长期团队协作内核 Spec

## 背景

MewCode 已具备主 Agent、一次性子 Agent、后台任务、跨启动会话恢复和 Git Worktree 隔离能力。现有子 Agent 以单个委派任务为生命周期，不能组成长期团队；成员之间没有共享任务清单或点对点邮箱，所有结果都只能回流主对话；应用重启后也不能按成员身份恢复协作上下文。

本阶段把主 Agent 扩展为 Team Lead，并建立长期团队协作内核。Lead 可以围绕用户目标维护一个长期团队，把目标拆成带简单依赖的任务，派生多个同进程协程成员并行执行。成员使用独立 Git Worktree，通过共享任务清单和持久邮箱直接协作；成员完成一轮工作后进入空闲状态，后续收到消息时可以从磁盘恢复原上下文继续工作。

本阶段只交付协程后端的完整闭环。独立终端窗格后端、后端自动选择、coordinator 模式和自动 Git 合并将在后续阶段实现。

## 目标

- 提供可跨 MewCode 重启复用的长期团队、成员花名册和 Team Lead 身份。
- 让 Lead 能把用户目标拆成带依赖的共享任务，并派生多个协程成员并行执行。
- 让团队成员通过共享任务清单和持久邮箱直接协作，不要求所有信息经 Lead 中转。
- 让每个成员在固定的独立 Git Worktree 中工作，避免并行修改互相覆盖。
- 为需要审批的成员建立“每次领取任务先提交计划、批准后才能修改”的强制流程。
- 让自然停止的成员进入空闲状态，并能在当前进程或进程重启后由新消息恢复原上下文。
- 保持普通主 Agent、现有一次性子 Agent 和非团队工作流的工具边界及行为不变。

## 功能需求

- F1: 系统必须支持创建、列出、打开和查看长期团队。团队名称在当前用户范围内唯一；团队必须记录名称、所属项目、负责人、成员花名册和持久化位置。
- F2: 团队必须持久化在 MewCode 用户数据区域中按团队名称隔离的目录内。重新启动 MewCode 后，团队配置、成员状态、任务清单、邮箱和成员上下文仍可恢复。
- F3: 每个主会话同一时间最多激活一个团队。打开团队后，当前主 Agent 成为该团队的 Lead；关闭当前团队只解除本会话的激活关系，不删除团队数据或停止长期成员。
- F4: 团队必须绑定创建时的 Git 项目。非 Git 项目不能创建团队；从其他项目打开团队时必须拒绝激活，并说明项目不匹配。
- F5: 成员花名册必须记录唯一名称、角色、固定工作目录、运行后端、是否需要审批、生命周期状态和上下文持久化位置。成员名称必须经过安全校验，不能借名称访问其他团队或任意文件路径。
- F6: 本阶段成员运行后端固定为同进程协程。请求本阶段不支持的后端时必须明确失败，不得静默改用协程后端。
- F7: 每个成员必须拥有固定且互不相同的 Git Worktree 和分支，并在后续任务及跨重启恢复时继续使用同一工作目录。主工作目录的未提交修改不得进入成员 Worktree，也不得因成员运行而被覆盖。
- F8: Lead 接到需要团队协作的用户目标后，必须先将目标拆成可执行任务并写入共享清单，再按任务依赖和并行条件派生成员。任务尚未写入清单时不得以团队成员身份开始执行对应工作。
- F9: 共享任务必须支持创建、读取、更新和删除，并至少记录任务标识、标题、说明、状态、直接依赖、负责人、创建者、创建时间、更新时间、完成结果和失败原因。Lead 和团队成员都可以使用共享任务能力。
- F10: 任务状态至少覆盖待处理、阻塞、进行中、等待审批、已完成、失败和已取消。每次状态变化必须持久化，并能识别变更发起者。
- F11: 任务依赖采用简单前置依赖：只有全部直接和间接前置任务均已完成，任务才可被领取或开始。系统必须拒绝不存在的依赖、自依赖和任何循环依赖；不支持条件分支、资源约束或部分完成触发。
- F12: 多个成员并发读取、创建、领取或更新任务时，系统必须保证单个变更原子生效。同一任务不能被两个成员同时成功领取；删除仍被其他任务依赖的任务必须失败。
- F13: 普通主 Agent 只能使用创建、列出和打开团队所需的生命周期入口，不能看到成员协作工具；现有一次性子 Agent 不得看到任何团队工具。只有激活团队后的 Lead 可以看到团队管理与编排能力；只有已注册团队成员可以看到共享任务和团队消息能力；成员不能派生或管理其他成员。
- F14: 系统必须为团队维护名称注册表，并通过注册表把成员名称和 Lead 名称解析到各自的邮箱。不存在、重复、已移除或跨团队的名称必须被拒绝，发件人身份必须由当前运行身份确定，不能由消息参数伪造。
- F15: 每个参与者必须拥有独立持久邮箱。每条消息至少包含唯一标识、发件人、正文、时间戳、已读状态和摘要；系统在落盘时自动补充时间戳，默认设为未读，并在未提供摘要时根据正文生成非空摘要。
- F16: 邮箱并发访问必须通过锁文件协调。锁暂时不可用时必须按有限策略重试；超过等待上限时返回明确失败。超过配置期限的旧锁可视为过期并被安全接管；任何锁失败都不能产生半条消息或破坏已有邮箱。
- F17: 团队消息必须支持点对点发送和广播。广播发送给团队内除发件人外的所有有效参与者，并返回逐个收件人的投递结果；部分投递失败时不得把已成功投递伪装成整体失败或重复发送。
- F18: 团队消息必须支持以下结构化协作协议：普通消息、任务指派、计划审批请求、计划批准、计划驳回、任务完成、任务失败、成员空闲、成员恢复和终止通知。协议消息必须携带其语义所需的任务或审批关联信息；不符合协议结构的消息必须拒绝投递。
- F19: 邮箱采用持久、可重试的投递语义。消息只有在成功交给目标成员上下文或被目标显式读取后才标记已读；读取失败或成员恢复失败时保持未读，依靠消息唯一标识避免同一条消息被重复加入上下文。
- F20: 运行中的成员在安全执行边界检查新消息，不要求中断正在进行的模型响应或工具调用。空闲成员收到有效新消息后必须被唤醒；同一成员任意时刻最多存在一个运行实例。
- F21: 每个成员必须拥有与 Lead 及其他成员隔离的消息历史、权限状态、上下文预算、文件读取缓存和运行状态。成员上下文必须持续写入磁盘，并能容忍末尾坏记录或未完成工具调用，不得因单个成员上下文损坏而破坏团队其他数据。
- F22: 成员自然完成一轮工作且不再请求工具时，必须结束当前协程、持久化安全上下文、标记为空闲并向 Lead 发送成员空闲消息。空闲不等同于退出团队，也不得删除成员工作目录或历史。
- F23: 当前进程内或 MewCode 重启后，向空闲成员发送新消息必须从其最近安全上下文恢复协程，并追加该消息继续执行，而不是创建同名新成员或从空白上下文重新开始。恢复成功后必须向 Lead 发送成员恢复消息。
- F24: 需要审批的成员每次领取新任务时，必须先生成计划并向 Lead 发送结构化审批请求；审批请求必须关联成员、任务和本次计划版本。成员等待审批期间可以读取和分析，但不能修改项目、提交变更或执行其他有副作用的操作。
- F25: Lead 必须通过结构化审批回复批准或驳回计划。批准消息必须精确关联当前待审批请求，批准后成员才能执行该任务的写操作；驳回消息必须包含理由，成员可据此修改计划并重新提交。过期、重复、任务不匹配或来自非 Lead 的审批回复不得解锁写操作。
- F26: 不需要审批的成员在任务满足依赖并成功领取后可以直接执行。审批要求只影响对应成员当前领取的任务，不能被其他任务的历史批准结果复用。
- F27: 成员完成代码修改类任务前必须把成果保存在自己的分支中，并在任务结果中提供可定位的成果信息；任务完成或失败时必须更新共享任务，并向 Lead 及受该任务直接影响的成员发送对应协议消息。
- F28: 成员正常完成、失败、等待审批、被终止或恢复时，花名册状态、当前任务和最后活动时间必须同步持久化。异常退出不得让任务永久伪装成进行中；Lead 必须能观察并重新指派未完成任务。
- F29: Lead 必须持续根据任务清单和邮箱处理依赖解锁、成员派发、审批决策、失败重派和完成汇总。在所有任务均已完成前，不得向用户宣称团队目标已完成；存在失败或取消任务且无法重派时，必须报告目标尚未达成。
- F30: 本阶段全部任务完成后，Lead 必须向用户汇总任务状态、成员成果和待集成分支，并明确说明尚未自动合并。若团队以失败或取消状态结束，则必须汇总未完成原因而不是给出成功结论。成员 Worktree、分支、邮箱和上下文继续保留，供后续任务或第三阶段集成使用。
- F31: Lead 必须能终止运行中、等待审批或空闲的成员。终止操作必须停止当前协程、持久化安全状态、解除其未完成任务占用并发送终止通知，但不得自动删除其上下文、Worktree、分支或已产生成果。

## 非功能需求

- N1: 团队、任务、花名册、邮箱和成员上下文的持久化必须可测试、可观察，不能只依靠提示词或进程内对象维持一致性。
- N2: 所有共享状态写入必须具备并发安全和故障安全；进程在写入中断后，已确认成功的数据必须可恢复，未确认的数据不得留下无法解析的半写状态。
- N3: 工具可见性、成员身份、审批前写入限制和 Worktree 边界必须由运行时机制强制执行，不能依靠成员自觉遵守提示。
- N4: 任一成员、邮箱、任务更新、锁获取、上下文恢复或 Worktree 操作失败，不得导致主 TUI 退出、Lead 会话损坏或其他成员停止工作。
- N5: 团队状态变化、失败原因、审批状态和恢复结果必须使用中文向用户或 Lead 展示，并避免暴露凭据等敏感信息。
- N6: 团队数据必须按团队和项目隔离；团队名称、成员名称、任务输入和消息内容不能造成目录穿越或访问其他团队数据。
- N7: 协程成员并行运行时不能通过切换进程全局工作目录影响 Lead 或其他成员；所有文件和命令操作都必须作用于成员自己的工作目录。
- N8: 邮箱和任务锁必须有明确等待上限与过期规则，不能无限阻塞 Agent Loop；旧锁接管和并发竞争必须留下可诊断结果。
- N9: 普通聊天、现有一次性子 Agent、后台任务、会话恢复、权限、Hook、上下文管理和 Worktree 清理策略不得因团队能力而回归。
- N10: 团队协作在支持的不同模型供应商下必须保持一致的用户可见语义，供应商差异不能改变任务、消息、审批和恢复规则。

## 不做的事

- 不实现独立终端窗格、终端复用器或其他独立进程成员后端。
- 不实现按环境优先级自动选择运行后端，也不实现终端窗格唤醒；这些属于第二阶段。
- 不实现 coordinator 双开关、Lead 写工具剥夺或 coordinator 专用工具集；这些属于第三阶段。
- 不自动合并、变基、挑拣或回滚成员分支，也不自动解决 Git 冲突；这些属于第三阶段。
- 不实现跨机器、跨用户或远程服务上的分布式团队。
- 不实现成员之间模型输出或工具执行过程的实时流式通信；消息只在安全执行边界投递。
- 不实现条件依赖、资源依赖、优先级调度、投票、仲裁或动态任务图优化。
- 不允许团队成员创建下级成员或嵌套团队。
- 不自动删除长期团队、成员上下文、成员 Worktree、分支或邮箱。

## 验收标准

- AC1: 在 Git 项目中创建团队后，团队名称、项目、负责人和持久化位置可被查看；退出并重启 MewCode 后仍能列出并打开该团队。（覆盖 F1、F2）
- AC2: 同一主会话不能同时激活两个团队；关闭后可以切换团队且数据仍保留。从非 Git 项目创建团队或从其他项目打开已有团队会明确失败。（覆盖 F3、F4）
- AC3: 添加成员后，花名册可观察到其唯一名称、角色、独立工作目录、协程后端、审批配置、状态和上下文位置；非法或重复名称在创建任何目录前被拒绝。（覆盖 F5、F6）
- AC4: 两个成员并行修改相同相对路径时分别写入不同 Worktree，主目录和对方目录不变；重启后成员继续使用原目录和分支。请求非协程后端会明确失败且不创建成员。（覆盖 F6、F7）
- AC5: 用户给 Lead 一个可并行目标后，共享清单中先出现带依赖的任务，再出现成员开始执行的状态；可并行任务可以由不同成员同时运行。（覆盖 F8、F29）
- AC6: Lead 和成员均能创建、读取、更新、删除合法任务；任务字段、状态变化、发起者和时间在重启后保持一致。（覆盖 F9、F10）
- AC7: 不存在依赖、自依赖、直接或间接循环依赖均被拒绝；前置任务未完成时下游任务不能被领取，完成后自动变为可领取；被依赖任务不能直接删除。（覆盖 F11、F12）
- AC8: 两个成员并发领取同一任务时恰好一个成功；并发更新或模拟写入中断后任务清单仍可解析，已确认变更不丢失。（覆盖 F12）
- AC9: 未激活团队的普通主 Agent 只能看到团队生命周期入口而看不到成员协作工具，现有一次性子 Agent 看不到任何团队工具；激活后的 Lead 能管理团队和任务，成员只能看到任务与消息能力且不能派生成员。（覆盖 F13）
- AC10: 成员按已注册名称直接给另一成员发消息后，目标邮箱出现一条不可伪造发件人的未读记录；未知、跨团队、重复或已移除名称发送失败。（覆盖 F14、F15）
- AC11: 未提供时间戳、已读状态或摘要的合法消息落盘后自动获得时间戳、未读状态和非空摘要，并保留唯一标识。（覆盖 F15）
- AC12: 邮箱锁短暂占用时发送方会重试并最终成功；锁超过等待上限时明确失败；旧锁可以被安全接管。三种情况下邮箱都不存在半条或损坏记录。（覆盖 F16）
- AC13: 广播会投递给除发件人外的全部有效参与者，并返回每个收件人的结果；模拟其中一个邮箱失败时，其他成功记录不重复也不丢失。（覆盖 F17）
- AC14: 普通、任务指派、审批请求、批准、驳回、任务完成、任务失败、成员空闲、成员恢复和终止消息均可被识别并校验；缺少任务或审批关联字段的协议消息不能投递。（覆盖 F18）
- AC15: 消息在成功加入目标上下文前保持未读，成功交付或显式读取后变为已读；恢复失败后重试不会把同一消息重复加入成员上下文。（覆盖 F19）
- AC16: 运行中的成员只在模型或工具执行之间接收消息，不中断正在执行的操作；空闲成员收到消息后被唤醒，且并发发送不会启动两个同名成员实例。（覆盖 F20）
- AC17: Lead、两个成员分别执行对话和工具后，其消息历史、权限、上下文预算、文件缓存和状态互不污染；单个成员上下文末尾损坏时能恢复到安全边界，其他参与者不受影响。（覆盖 F21）
- AC18: 成员自然停止后协程结束、状态变为空闲、上下文落盘且 Lead 收到空闲消息；其 Worktree、分支、花名册和历史仍存在。（覆盖 F22）
- AC19: 在同一进程和重启后的两个场景中，Lead 给空闲成员发送新任务消息，成员都从原上下文和原 Worktree 恢复，能引用之前工作，并向 Lead 发出恢复消息。（覆盖 F23）
- AC20: 需要审批的成员领取任务后先发送关联任务和计划版本的审批请求；等待期间读取操作可用，但项目修改、提交和其他副作用操作均被系统拒绝。（覆盖 F24）
- AC21: Lead 用匹配当前请求的结构化批准消息后，成员可以开始修改对应任务；其他成员、旧计划、错误任务或重复批准消息都不能解锁写操作。（覆盖 F25、F26）
- AC22: Lead 驳回计划并给出理由后，成员能修改计划并提交新版本；新版本获批前仍不能写入，历史批准不能复用。（覆盖 F25、F26）
- AC23: 代码修改任务完成时，成员分支包含可定位成果，任务清单记录结果，Lead 和直接受影响成员收到完成消息；失败时任务记录原因并收到失败消息。（覆盖 F27）
- AC24: 成员完成、失败、等待审批、被终止和恢复后，花名册状态、当前任务和最后活动时间均正确；异常退出后 Lead 能观察任务未完成并重新指派。（覆盖 F28、F31）
- AC25: 终止运行中、等待审批或空闲成员后，不再存在其运行协程，未完成任务不再被其占用；上下文、Worktree、分支和已有成果仍保留，并产生终止通知。（覆盖 F31）
- AC26: 存在未完成、阻塞、等待审批、失败或取消任务时，Lead 不会报告团队目标完成；全部任务完成后，Lead 汇总成员成果和待集成分支并明确未执行自动合并；无法重派的失败或取消任务会产生未达成报告。（覆盖 F29、F30）
