# Prompt Cache Hit Rate Spec

## 背景
JulyCode 已经把稳定提示和运行时补充分离，并能在状态栏展示供应商返回的缓存状态。当前调查发现，稳定提示内容较短，单靠固定说明不一定达到缓存门槛；运行时补充每轮都会变化；长对话中历史消息持续增长时，如果没有合适的缓存边界，供应商可能只能反复写入缓存而较少读取缓存。

OpenAI 官方说明缓存需要精确前缀匹配，静态内容应放在开头，动态内容放在末尾，并通过 `cached_tokens` 观测命中；Anthropic 官方说明缓存读取只会查找之前已经在断点写入的前缀，断点放在每轮变化的内容上会导致持续 miss。

## 目标
- 提高连续对话、工具调用循环和子 Agent 复用相同上下文时的提示词缓存命中机会。
- 保持模型可见的系统约束、运行时补充、工具定义、对话历史和工具结果语义不变。
- 让缓存命中、写入、未命中和未知状态继续可观测，便于后续判断效果。
- 对不支持相关缓存能力的供应商或兼容接口保持向后兼容。

## 功能需求
- F1: 连续请求中相同的静态说明、工具定义和已确认不变的对话前缀应尽可能位于供应商可复用的缓存前缀中。
- F2: 每轮变化的运行时信息、临时注入、当前用户目标和上下文摘要不得破坏前面已经可缓存的静态前缀。
- F3: 对支持显式缓存边界的供应商，应在不会改变对话语义的位置写入缓存边界，避免只在变化内容后写缓存。
- F4: 对支持缓存路由提示或缓存保留策略的供应商，应使用稳定且低风险的默认策略提升连续请求命中机会。
- F5: 缓存优化不得改变工具调用协议、工具结果关联、消息顺序约束、错误处理和流式输出行为。
- F6: 缓存观测应继续准确反映供应商 usage 字段，且在字段缺失或不支持时仍显示 unknown 或 unsupported。
- F7: 文档应说明缓存命中依赖供应商策略、模型、请求间隔和请求内容，JulyCode 只能提高命中概率，不能保证每次命中。

## 非功能需求
- N1: 改动应局限在提示构造、请求序列化、配置解析、文档和相关测试，不引入新的外部依赖。
- N2: 默认配置应保持现有用户无需迁移即可运行。
- N3: 优化不得引入敏感信息进入缓存分组标识或日志。
- N4: 单元测试应覆盖请求 payload、缓存断点、配置默认值和 usage 解析。
- N5: 端到端验收应使用 tmux 启动 JulyCode，输入真实对话请求，并观察工具调用与缓存状态展示。

## 不做的事
- 不实现本地 KV cache、向量缓存或代理层缓存。
- 不改变供应商计费、缓存 TTL 或实际缓存命中结果的判定逻辑。
- 不为了命中缓存而删减必要的运行时约束、权限约束、Skill 约束或项目指令。
- 不切换默认模型、默认协议或默认 API 端点。
- 不引入会影响回复质量的提示压缩或语义重写。

## 验收标准
- AC1: 连续同一会话请求的静态说明和工具定义保持稳定，动态运行时内容不会出现在静态缓存边界之前。（覆盖 F1、F2、F5）
- AC2: 支持显式缓存边界的请求会在稳定前缀和必要的历史增长点设置可观测的缓存边界，且不会放在每轮变化的运行时补充之后。（覆盖 F3、F5）
- AC3: 支持缓存路由提示或缓存保留策略的请求会携带稳定、安全、可配置的缓存优化参数；禁用或未配置时仍能正常请求。（覆盖 F4）
- AC4: usage 中已有的缓存字段继续被解析为 hit、write、miss 或 unknown，字段缺失时不会影响对话。（覆盖 F6）
- AC5: 项目文档解释优化策略、限制和观测方式，避免承诺供应商必然命中。（覆盖 F7）
- AC6: 相关单元测试和 tmux 端到端场景通过，JulyCode 能正常调用工具并生成回复。（覆盖 F1-F7、N4、N5）
