# MewCode 上下文管理 Spec

## 背景
MewCode 当前已经具备全屏对话、结构化系统提示、工具调用、Agent Loop、Plan Mode、权限控制和 MCP 工具接入。会话历史会在当前运行期持续累积，模型请求会携带用户消息、助手消息、工具调用和工具结果。随着任务时间变长，工具结果尤其容易成为 Token 大头；一旦上下文逼近模型窗口上限，后续请求可能失败，导致长任务中断。

本阶段要为 MewCode 增加上下文管理能力。系统需要优先压缩工具结果，并在整体历史逼近窗口上限时用结构化摘要替换较早历史，使 MewCode 能在有限 Token 预算内继续长时间完成编程任务。

## 目标
- MewCode 可以在每次模型请求前主动控制上下文体量，降低上下文溢出风险。
- MewCode 可以优先处理超大的工具结果，把完整内容保存到可重新读取的位置，并在对话里保留预览、路径和必要元数据。
- MewCode 可以在整体历史接近窗口上限时生成结构化摘要，压缩较早消息，同时保留近期消息原文。
- MewCode 可以尽量保留用户原始消息，不在轻量预防阶段改写用户输入；在重量兜底阶段被摘要覆盖的历史用户内容必须明确作为摘要信息呈现，不能伪装成原文。
- 用户可以用 `/compact` 手动触发上下文压缩。
- 摘要连续失败时，系统可以熔断，避免在同一类失败上无限重试。

## 功能需求
- F1: 每次发起模型请求前，MewCode 必须先执行轻量预防，再评估是否需要重量兜底。
- F2: 轻量预防必须以工具结果为主要压缩对象；普通用户原始消息不得因为轻量预防被摘要、改写或删除。
- F3: 当单个工具结果超过单结果阈值时，MewCode 必须把完整工具结果保存到可重新读取的位置，并在会话中只保留工具名称、调用标识、成功或失败状态、简短预览、内容规模信息和保存路径。
- F4: 当同一轮工具结果合计超过轮次阈值时，MewCode 必须优先选择体量最大的工具结果依次保存到外部位置，直到该轮工具结果在会话中的保留内容降到阈值内或没有可继续压缩的工具结果。
- F5: 轻量预防后的工具结果预览必须清楚提示内容已被外置保存，并说明需要完整细节时应重新读取保存路径。
- F6: 大型失败结果、命令输出、文件内容、搜索结果和远端工具返回内容都必须适用同一套轻量预防规则。
- F7: MewCode 必须维护上下文规模估算；估算优先锚定最近一次模型接口返回的 Token 用量，后续新增内容可以用字符数近似换算，供应商没有返回用量时也必须能继续估算。
- F8: 自动触发重量兜底时，MewCode 必须在估算上下文接近窗口上限前保留 13K Token 安全余量，以抵消估算误差。
- F9: 用户输入 `/compact` 时，MewCode 必须手动触发重量兜底，并将安全余量收窄到 3K Token；该指令不应作为普通任务交给模型继续执行。
- F10: 重量兜底必须压缩较早的会话历史，并从尾部按估算 Token 往回保留近期原文；近期原文保留范围应约 1 万 Token，且无论估算如何至少保留最近 5 条消息。
- F11: 重量兜底生成的摘要必须使用固定结构组织，至少覆盖当前目标和约束、用户明确要求、已完成工作和关键决策、重要文件或工具结果索引、待办事项和阻塞、验证状态与风险。
- F12: 摘要生成请求必须明确禁止模型调用任何工具；摘要生成过程必须要求先产出分析草稿再产出正式摘要，草稿只能用于生成正式摘要，不能写入压缩后的会话历史。
- F13: 压缩后的会话必须补充一条清晰的边界提示，提醒后续模型：摘要和预览不是完整事实来源，如需文件或工具结果细节必须重新读取对应路径，不得凭摘要脑补代码细节。
- F14: 重量兜底必须保留当前任务所需的关键状态，包括当前用户目标、运行模式、未完成计划、最近工具调用结果、权限或错误状态；这些状态可以保留原文或进入结构化摘要，但不得丢失。
- F15: `/compact` 执行完成后，MewCode 必须向用户展示压缩结果摘要，包括是否执行了压缩、保留了多少近期消息、外置保存了哪些大结果或生成了摘要。
- F16: 当摘要生成失败时，MewCode 必须记录连续失败次数；连续失败达到 3 次后必须熔断，停止继续自动重复摘要，并向用户说明上下文压缩暂时不可用。
- F17: 熔断后，MewCode 不得在同一次请求链路中继续反复尝试摘要；如果估算上下文仍可能溢出，系统必须停止本次模型请求并给出可理解提示，而不是冒险发送明显超预算的请求。
- F18: 一次成功的重量兜底必须清除此前的连续摘要失败状态。
- F19: 上下文管理不得破坏现有普通聊天、工具调用、工具结果回灌、Plan Mode、`/do` 执行、权限确认、流式显示和错误恢复行为。
- F20: 上下文压缩产生的外置内容路径必须能被后续可用的读取工具重新读取，使模型可以在需要时取回完整细节。

## 非功能需求
- N1: 本阶段不要求精确 tokenizer；Token 规模估算只需足以稳定触发轻量预防和重量兜底。
- N2: 压缩策略应保持确定、可解释、可测试，不引入机器学习或自动调参策略。
- N3: 压缩过程不得泄露配置密钥或其他敏感信息；外置内容和摘要都必须延续现有脱敏要求。
- N4: 压缩失败、摘要失败或外置保存失败不得导致 TUI 退出、会话状态损坏或后续输入不可用。
- N5: 自动重量兜底只应在接近上下文上限时触发；普通短对话和小工具结果不应额外产生摘要请求。
- N6: 上下文管理行为必须对不同模型供应商保持一致；供应商差异不得泄漏到用户交互层。
- N7: 用户可见提示必须使用中文，说明应具体到用户能判断下一步该继续、手动压缩还是重新读取文件。

## 不做的事
- 不实现精确 tokenizer 或按供应商逐模型维护精确计数表。
- 不实现摘要策略的机器学习优化、自动评分器或多摘要候选选择。
- 不实现跨启动的会话历史恢复、长期记忆或自动记忆沉淀。
- 不把用户近期原始消息改写成摘要，也不在轻量预防阶段压缩普通用户消息。
- 不保证摘要可替代完整文件或完整工具结果；需要细节时必须重新读取原始来源。
- 不实现二进制附件、多模态内容或图片内容的专门压缩策略。
- 不改变现有工具本身的业务能力、权限规则或沙箱边界。

## 验收标准
- AC1: 当单个工具结果超过阈值时，下一次模型请求中不再包含该结果全文，而是包含预览、内容规模信息和可重新读取的保存路径。
- AC2: 当同一轮多个工具结果合计超过阈值时，系统优先外置保存最大的结果，直到该轮保留内容降到阈值内；较小且未超限的结果仍可保留原文。
- AC3: 轻量预防触发后，用户原始消息在会话中仍保持原文，不被摘要或改写。
- AC4: 当整体上下文估算接近窗口上限时，自动重量兜底会在保留 13K Token 安全余量前触发，并用结构化摘要替换较早历史。
- AC5: 用户输入 `/compact` 后，系统使用 3K Token 安全余量执行手动压缩，并返回压缩结果说明；该指令不会启动普通 Agent Loop 任务。
- AC6: 重量兜底后，最近约 1 万 Token 或至少最近 5 条消息以原文保留，较早内容进入结构化摘要。
- AC7: 生成并保存的正式摘要包含固定结构部分，覆盖当前目标、用户要求、已完成工作、关键索引、待办阻塞、验证状态和风险。
- AC8: 摘要生成请求不携带任何可用工具；摘要草稿不会进入压缩后的会话历史，只有正式摘要被保留。
- AC9: 压缩后的会话包含边界提示，明确要求模型需要细节时重新读取文件或工具结果路径，不能按摘要脑补代码。
- AC10: 外置保存的工具结果路径可以通过读取工具取回完整内容，后续模型能基于该路径继续工作。
- AC11: 当供应商返回 Token 用量时，后续估算会以该用量为锚点；当没有用量时，系统仍能用近似估算触发压缩，不中断任务。
- AC12: 摘要连续失败 3 次后，系统进入熔断状态，不再无限重复摘要；如果上下文仍可能溢出，本次请求停止并显示清晰原因。
- AC13: 一次成功的重量兜底会清除连续摘要失败状态，后续自动压缩可以正常工作。
- AC14: 压缩前后，普通聊天、工具调用、工具失败回灌、Plan Mode、`/do` 和权限确认的既有行为仍通过原有测试。
- AC15: 在端到端场景中，用户要求产生大工具输出后继续追问，MewCode 能先外置保存大结果，再让模型通过保存路径重新读取需要的细节并继续回复。
