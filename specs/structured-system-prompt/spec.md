# MewCode Structured System Prompt Spec

## 背景
MewCode 已经具备终端对话、工具调用、Agent Loop 和 Plan Mode。当前模型请求主要由会话消息和工具描述组成，缺少统一的全局系统提示结构，也没有把长期稳定指令、运行环境信息、会话级模式指令和动态补充指令清晰分层。

这会带来几类问题：稳定指令无法稳定复用缓存，环境信息和模式指令容易与用户输入混在一起，模型对关键工具规则的遵守依赖零散提示，缓存命中效果也缺少明确观测。本阶段要把全局提示从简短文本升级为结构化系统提示，让 MewCode 在保持现有对话和工具能力的基础上，更稳定、更低成本地指导模型完成编程任务。

## 目标
- MewCode 可以按职责和优先级组织全局系统提示，使基础行为约束稳定、清晰、可扩展。
- MewCode 可以区分稳定提示内容和动态运行内容，让稳定内容具备可缓存条件，动态内容通过系统级补充方式按轮次注入。
- MewCode 可以在全局提示和工具描述中同时强化关键工具规则，提高模型对专用工具、先读后改、安全边界和模式约束的遵守率。
- MewCode 可以用可观测方式记录供应商返回的缓存使用情况，验证缓存策略是否实际生效。
- MewCode 可以在现有两类模型供应商协议上提供一致的提示行为；当某个协议不支持同等缓存能力时，系统必须明确降级且不影响正常对话。

## 功能需求
- F1: MewCode 必须把全局系统提示拆分为固定模块，固定模块至少覆盖身份、系统约束、任务模式、动作执行、工具使用、语气风格和文本输出。
- F2: 固定模块必须按明确优先级拼装，模块之间保持清晰分隔；基础固定模块之后必须能接入环境信息，以及自定义指令、已激活能力说明和长期记忆等可选模块。
- F3: MewCode 必须把稳定内容和动态内容分开处理。稳定内容包括固定全局提示和稳定工具描述；动态内容包括运行环境、当前轮次模式指令、会话状态和对话历史。
- F4: 稳定内容必须优先进入供应商可缓存的提示通道；如果当前供应商或配置无法使用缓存，MewCode 必须继续正常请求，并保留可观测的降级状态。
- F5: 动态运行信息必须通过系统级补充消息注入，不得作为普通用户请求文本拼接进用户消息，也不得污染稳定提示缓存。
- F6: 系统级补充消息必须带有明确边界标签，使模型能识别它是运行时控制信息，而不是需要直接回复的用户输入。
- F7: 会话级开关和模式指令必须按轮次控制注入频率：首次启用时注入完整说明，间隔轮次重复关键规则，其余轮次只注入精简状态。
- F8: Plan Mode 的规划阶段指令必须通过系统级补充消息表达，保持只读规划约束；执行阶段必须通过系统级补充消息表达可执行计划和全工具能力状态。
- F9: 工具描述必须强化工具自身适用场景和关键约束，尤其是优先使用专用工具、读取或搜索后再编辑、写入和命令执行的影响边界、错误结果如何继续处理。
- F10: 全局系统提示也必须强化与工具描述一致的关键规则，形成全局规则和工具规则的双重约束。
- F11: MewCode 必须在每次模型请求中保持当前对话历史的正常上下文能力，不能因为引入系统提示、缓存或补充消息而丢失多轮对话、工具调用和工具结果。
- F12: MewCode 必须解析当前供应商返回的缓存相关用量字段，并通过统一的用量观测结果暴露缓存命中、缓存写入或未知状态。
- F13: 当供应商返回的缓存字段缺失、格式变化或不可用时，MewCode 不得中断对话，必须把缓存观测标记为未知或不可用。
- F14: MewCode 必须支持一组典型人工对比场景，用于观察结构化提示上线前后在工具选择、编辑前读取、Plan Mode 约束、动态环境注入和缓存命中上的差异。
- F15: 本阶段必须覆盖现有两类模型供应商协议的请求构造、缓存观测和降级行为，使用户在两类协议下获得一致的系统提示体验。

## 非功能需求
- N1: 系统提示结构必须可扩展，新模块可以按优先级插入，不需要重写已有模块或破坏现有模块顺序。
- N2: 稳定提示内容应保持确定性；相同配置、相同工具集和相同稳定模块在不同轮次中应生成一致内容，以利于缓存命中。
- N3: 动态补充消息应尽量短小，只包含当前轮次需要的运行信息和模式约束，避免无意义增加输入成本。
- N4: 提示内容必须使用中文表达，并与 MewCode 当前面向中文用户的交互风格一致。
- N5: 新增提示策略不得降低现有普通聊天、工具调用、Plan Mode、流式显示、用量展示和错误恢复能力。
- N6: 缓存观测必须是可测试、可记录的结构化信息，而不是只依赖界面文本或日志描述。
- N7: 敏感信息不得进入稳定可缓存内容；环境信息和动态补充消息也不得泄露完整密钥或其他需要脱敏的值。
- N8: 当不同供应商对系统提示、工具描述或缓存字段的能力不一致时，差异必须被封装在供应商边界内，不应泄漏到用户交互层。

## 不做的事
- 不实现项目指令文件加载。
- 不实现自动记忆、长期记忆生成或跨启动记忆恢复。
- 不实现真实 MCP 接入或外部工具市场。
- 不实现自动化评估平台、打分器或批量基准测试。
- 不引入权限确认、危险命令审批或新的沙箱隔离机制。
- 不要求本阶段改变工具本身的文件读写、搜索或命令执行能力。
- 不要求所有供应商具备完全相同的缓存能力；只要求支持时启用，不支持时明确降级并可观测。

## 验收标准
- AC1: 模型请求中存在按优先级排列的结构化全局系统提示，固定模块覆盖身份、系统约束、任务模式、动作执行、工具使用、语气风格和文本输出。
- AC2: 环境信息和可选模块位于固定模块之后，并与固定模块保持清晰边界；未启用的可选模块不会产生空占位。
- AC3: 连续两轮相同工具集和相同稳定配置下，稳定提示内容保持一致；当前工作目录、模式状态或会话历史变化只影响动态注入部分。
- AC4: 支持缓存的供应商请求中，稳定全局提示和稳定工具描述进入可缓存通道；不支持缓存时请求仍能正常完成，并暴露降级状态。
- AC5: 动态环境信息和模式指令以带边界标签的系统级补充消息出现，不作为普通用户输入发送，也不会进入稳定缓存内容。
- AC6: Plan Mode 首轮包含完整规划约束，间隔轮次重复关键规则，普通轮次只包含精简模式状态；`/do` 执行阶段能注入当前待执行计划和全工具能力状态。
- AC7: 工具描述和全局系统提示同时包含关键工具规则，模型请求中能观察到专用工具优先、编辑前读取、写入和命令边界等约束。
- AC8: 普通多轮对话、工具调用、工具结果回灌和最终回复在引入结构化提示后仍保持现有行为。
- AC9: 系统能从供应商返回中提取缓存命中、缓存写入或未知状态，并通过统一用量观测结果提供给上层。
- AC10: 供应商没有返回缓存字段或返回不可识别字段时，本次对话不失败，缓存观测结果显示为未知或不可用。
- AC11: OpenAI 和 Anthropic 两类现有供应商协议都能使用新的提示构造流程；其中任一协议缓存能力不足时只影响缓存状态，不影响系统提示注入和正常回复。
- AC12: 典型人工对比场景可以覆盖工具选择、编辑前读取、Plan Mode 只读约束、动态环境注入和缓存观测，且每个场景都有明确可观察结果。
